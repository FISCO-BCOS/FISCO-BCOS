## 你的范围

## 你的问题

1. **文件尺寸与职责**:`EngineServiceImpl.h` 现在 +926 行(总量请自己 `wc -l`),`OpSchedulerImpl.h` +937 行,两个都是**头文件里的类模板实现**。
   - 每个文件承担了几件事?能不能说清"这个文件负责什么、怎么用、依赖什么"?
   - 该拆吗?如果该拆,拆在哪条缝上(给出具体的文件划分与每个新文件的职责),以及**拆分的代价是什么**(模板实现必须在头里、`c_opMode` 的 SFINAE 探针依赖完整类型、编译期开销)。
   - 如果你的结论是"不该拆",说清理由——本仓既有代码的惯例是什么(去看 `bcos-evm/` 与 `engine/` 里同类文件的规模与组织方式,不要凭空定标准)。
2. **`c_opMode` 双模式的组织代价**:同一个类模板同时服务通用与 OP 两种 `SchedulerType`,靠 `if constexpr` 分流。
   - 数一下有多少个 `if constexpr (c_opMode)` 分支、分散在多少个函数里。
   - 这个设计的**失效模式**是什么:探针基于成员函数签名做 SFINAE,签名一改探针静默变假,OP 请求落进通用分支。护栏现在在哪、够不够?
   - 有没有更好的组织方式(策略类特化 / 独立的 OP 派生类 / 把 OP 路径整体抽成独立组件)?给出**至少一个具体替代方案的骨架**并诚实评估迁移成本,不要只说"应该解耦"。
3. **接缝设计**:`OpEngineSeam.h`(+187)是 engine 层与 OP 实现之间的接缝。它是一个好接缝吗?——判据:能不能不读 `OpSchedulerImpl.h` 就理解 engine 侧在依赖什么;换一个 OP 实现要改几个地方;接缝里有没有泄漏实现细节的类型。
4. **重复**:找**复制粘贴的逻辑块**。本仓有过一处实证:同一条 `yParity > 1` 校验在两个复制的地方各写一遍,导致"测了一处 ≠ 另一处也对"。用 `rtk grep` 找同类:相似的解码分支、相似的校验序列、相似的错误构造。每找到一处,给出两个位置的 `file:line` 并判断是否应当合并(合并的风险是什么)。
5. **依赖方向**:`engine/` → `bcos-evm/` → `bcos-codec/` → `bcos-framework/`。核对有没有反向依赖或跨层直连。特别看:`engine` target 有没有链接 `bcos-codec`(已记账一条:`EthBlockHeader::decode` 目前靠**测试二进制**传递链接,生产组合根接入时须处理——请核实这条是否属实,以及它现在是不是一个会在集成时爆炸的定时炸弹)。
6. **命名**:表名常量、函数名、异常类型名。找**名字与实际行为不符**的(本批已知一处主动披露:`ValidPayloadRegistersAllFourTables` 现在写五张表,实施者为保可追溯性故意不改名——请判断这个取舍是否成立)。
7. **CMake**:`bcos-evm/test/CMakeLists.txt` +80 行。核对:测试目标的组织、`UNITY_BUILD` 与匿名命名空间同名类型的冲突风险、`${CMAKE_SOURCE_DIR}` 进 include 路径的作用范围、以及那条"编入源码 vs 链 engine 库二选一"的护栏——它是靠注释还是靠真实的 CMake 断言?
