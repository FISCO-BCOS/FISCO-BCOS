## 四、关键 finding 的证据细节

### F1（最有价值的一条）

- 基线：`BoostLogInitializer.cpp` 中 `m_autoFlush = _pt.get<bool>("log.flush", true)` → boost `auto_flush(true)`，每行落盘。
- 首提交：同一处改为 `false`（`2ae3a635:BoostLogInitializer.cpp:136`），而当时的 `feedLoop`（`2ae3a635:LineAsyncSink.h:205-232`）**只在 `m_flushRequested` 为真时 flush**，即运行期没有任何周期性刷盘。
- 评审引用"作者自己给 `ci_check_air.sh` 注入 `flush=true`"作为佐证，论证方式成立；模板（`tools/BcosBuilder/src/tpl/config.ini.*`、`build_chain.sh` 的 `[log]` 段）确实不含 `flush` 键。
- 修复与评审首选建议一致：队列排空即刷 + 洪泛下按 `FlushInterval` 兜底。

### F2 / F3（安全语义）

- `std::abort()` 不刷 C++ 流、不执行静态对象析构；FATAL 的 abort 决策在消费端（backend 的 `consumeLine`），因此"丢一条 FATAL"等于丢掉了终止动作。
- 基类为无界队列，确实不会丢记录，所以这是本 PR 新引入的 fail-open。
- 修复同样按评审建议：FATAL 在生产者线程同步写（`LineAsyncSink.h:134-151`），backend 在 `std::abort()` 前 flush（`BoostLogInitializer.cpp:365/375`）。

### F4（基类比对）

- 被删除的 `BoostLogThreadNameAttribute.h`（base）用 `name.empty() ? "Unnamed" : name` **逐条求值**；`Common.cpp`（base，`185-231`）在 `pthread_getname_np` 返回空名时置空，并在非 `__GLIBC__`/`__APPLE__` 平台**无条件清空** → Windows 上每行的线程名都为空。
- 新代码 `cachedName` 与 `part` 同时为空，首次比较 `cachedName != name` 为 false，`part` 永不构建 → 审批评审"字段数变化、破坏按位置解析"的判断正确。
- 修复即评审给出的方案：独立的 `initialized` 标志。

### F6（算术核对）

- 32768 × 2 KB ≈ 64 MiB；32768 × 32 KB ≈ 1 GiB；空载 `Slot`（`std::string` 32B + `LogLevel` 4B + padding ≈ 40B）× 32768 ≈ 1.3 MB；free-list `deque<uint32_t>` 另约 128 KB/sink。评审数字无误。
- 修复：超过 4 KB 的槽在归还池前换新串（`LineAsyncSink.h:228` 与 `feedOne` 内的 swap）。

### Copilot-A

- `2ae3a635:LineAsyncSink.h:212-220` 的 `m_backend->flush()` 不在任何 `try` 内：异常会穿出 `feedLoop()` 线程函数 → `std::terminate`；同时 `flush()` 的调用方永远等不到 `m_flushDone`。属于 FIB-184 同型漏洞，Copilot 判断正确。

## 五、评审意见中的三处不准确

1. **F5 过期**（详见第三节）：评审 narrative 以 `2ae3a635` 为准，但其提交锚定的是 `0cf2319f18`——该提交正是修 `ERROR` 宏的，注释里的推理与评审 F5 完全一致。评审自己在"Verification boundary"中声明未编译，F5 正是这类静态推断的产物。
2. **F7 的一处论据错误**："this PR removed every `core->set_logging_enabled` call" 不成立。本 PR 只删除了 `BoostLogInitializer` 中的 3 处生产调用；测试夹具中仍有数十处（`bcos-executor/test/**`、`bcos-pbft/test/**` 等，`2ae3a635` 与 HEAD 均是）。因此被批评的那句注释（防止其他套件关掉共享 core）在当时是有必要的。F7 的主结论（新管线无测试、FIB-184 不再指向生产代码）不受影响。
3. **F1 中 `ci_check_pro.sh` 的影响被放大**：`grep -i reachN` 确实存在（`:171`），但 `.github/` 下没有任何 workflow 引用 `ci_check_pro.sh` / `ci_check_baseline.sh`；CI 只跑 `ci_check_air.sh`、`ci_check_eth_executor.sh`、`ci_check_single_node_consensus.sh`。真在 CI 中的是 Copilot 指出的 `ci_check_eth_executor.sh`。

2. **PR 描述未更新**（F10 的描述部分未闭环）：仍写着 "byte-identical (verified by diff)"、"Drop `BoundedAsyncSink`"、"Remove the no-longer-needed boost-lockfree vcpkg dependency"、以及已被 `45ac218e` 回退的 "ci_check_air.sh 注入 flush=true"。现在比评审时更不准确，建议一并更新。
3. **未提交的共享 `LineFeeder`（单例喂食线程）是评审从未覆盖的新并发面**，建议单独评审并补测试，重点：
   - 在 worker 线程内触发 `stop()` 是否会自死锁（`removeClient` 等待 `m_active` 清空）；
   - `stop()` 先内联排空、再 `removeClient` 的顺序假设；
   - 某个 sink 队列长期非空时，其他 sink 的调度饥饿；
   - `LineAsyncSinkTest` 目前是 `SKIP_UNITY_BUILD_INCLUSION`，新增并发用例的稳定性。
4. F6 的"池大小可配置"未采纳——可接受，但建议在注释里写明 `32768 × 4 KB` 的最坏上界。
5. F11 保留参数（已注明忽略）是可接受方案；若后续有 SDK 大版本，再连同 `log.format` 一起清理。
